## 文本筛选系统性缺陷：编码前六问

失败输入：ABC→合理澄清；明确补充“部件名称包含 ABC”→错误拒绝支持。保留用户截图与原V1提示词，不修改原数据。

1. 类别：意图协议表达不足，跨模型适配/执行/上下文/UI的共享机制缺陷。
2. 不变量：明确且支持的筛选条件必须完整进入执行器；无结果与不支持不可混同；所有结果可追溯原行；续问不得无声丢条件。
3. 失效机制：只有operation/entity/scope，不能表示筛选；服务只存对象不存查询；UI无条件推荐报警。
4. 最低责任层：结构化查询协议与共享白名单过滤器；模型负责语义，数据库负责事实。不是关键词识别或ABC特判。
5. 抽象：search操作+target+filters（AND文本条件），可选父对象与direct/all；字段和操作校验，不可执行自由SQL；查询快照入会话，空结果仍保留条件；重新提问或清除才改变范围。
6. 矩阵：设备/部件/PBS/类别/测点；名称vs编码；精确/包含/前缀/不包含/空值；多个条件；直接/递归；无结果/多结果/分页/原行；条件续问/替换/新话题/澄清；SQL注入、未知字段及旧查询回归。

范围界限：不引入行业推断、编辑数据、模糊名称自动认定唯一实体、数值/日期范围或任意OR表达式。unsupported条件必须澄清，不能忽略。回退：V1提示词保留，可回退适配与调用；无持久数据库迁移。需要重启本项目进程使代码生效，旧会话失效，新对话验证。

## 多问题漏答：系统性六问与验证计划

失败原句：构型MOHB01有哪些部件？哪些测点开启且已报警。原返回只有parts/MOHB01/direct，第二问被丢弃。
1. 类别：整个链路的单任务假设，属于跨协议、执行、会话、页面的系统性问题。
2. 不变量：每个用户意图有对应结果或明确未执行原因；独立任务不能互相污染条件；多结果不能偷偷取最后一项当唯一上下文。
3. 机制：一个operation→一个result→一个分页ID→一个context。提示词与校验均无多任务结构。
4. 公共责任层：查询计划契约与服务编排层；原只读执行器不承担自然语言拆句。
5. 通用方案：batch含2—4个task（每个question+完整intent），一次模型请求，分项执行、证据、分页与错误；先全量校验，再执行；后续context保存branches，未明确指向时澄清，不默认最后项。依赖前一结果而无法确定实体的子任务明确澄清，不伪造跨树映射。
6. 矩阵：两独立查询/多条件单查询/同对象多个操作/混合帮助/部分失败/缺数据/多个结果代词/明确第一项追问/嵌套或超限计划/分页隔离/取消/旧单任务回归。
不做：关键词或标点拆句、无限任务数、模型自由SQL、构型自动反推现场。原V3保留；无数据库迁移；重启仅本项目服务。
