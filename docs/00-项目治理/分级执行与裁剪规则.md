# 分级执行与裁剪规则

版本：1.2。本文是执行分级的唯一源，由 AGENTS.md 引用。分级调整记录深度和验证范围，不改变业务事实、授权、安全、语义治理与验收真实性要求。

## 母版入口与范围

本规则面向软件研发。is_template: true 时采用：Audit 只读审计，不初始化、不登记门禁、不生成运行记录；TemplateMaintenance 维护母版，依据用户请求记录影响、修改前快照、版本和验证；TemplateRegression 检查母版结构及合成项目，保留隔离证据。母版执行记录可集中写入升级说明，不填写业务门禁或伪造业务确认，也不初始化母版 Git。

scripts/Test-TemplateRegression.ps1 负责完整模板清单及可选模块存在性；scripts/Test-ProjectReadiness.ps1 负责业务项目当前入口真正适用的文件、状态和门禁。Structure 是轻量登记结构检查，不证明母版完整或业务验收。Audit、TemplateMaintenance、TemplateRegression 是母版入口标识；Readiness 仅校验其身份/基础路由，TemplateRegression 的实际验证由回归脚本执行。

阶段 Prompt 是入口和门禁，不是人为停止点。用户已要求初始化后的开发、验证或修复时，完成必要门禁后继续，不仅因阶段变化重复询问。Audit 的只读边界优先于登记要求。

## 先选择本轮工作入口，再判断风险

|入口|什么时候使用|进入条件|记录方式|
|-|-|-|-|
|首次开发 Startup|新项目第一条可用闭环|用户已明确目标、使用者、输入输出、范围外与验收；AI已完成本闭环必要的技术和风险检查|一份启动简表、一条 startup_scope_confirmed 综合确认；严格档另有风险评审|
|日常迭代 Iteration|已有业务基线下的新增、修复和优化|引用已有基线与本次请求，明确影响和验证计划；只检查受影响的设计门禁|AI维护本轮变更.json；不重做全套需求分析，不重新确认无变化内容|
|正式发布 Release|向目标环境发布或正式交付|当前范围对应的完整设计、测试、版本、授权、恢复与交付证据|复用已有记录补齐差额，执行完整发布门禁|

Development 保留为2.6兼容的完整设计评审入口，不是新项目默认启动或每轮迭代前置步骤。Startup/Iteration 通过只表示可以开始所声明范围的实现，不代表测试通过或可发布。

所有档位先用一份简短启动记录，不要求先填满全部文档。文件名“轻量项目执行简表.md”为兼容路径，首次开发各档均可使用；档位决定必要设计深度，不能用简表绕过敏感数据、权限或其他安全设计。复杂业务可以引用详细专项内容，无需复制。

### 首次开发

用户只需集中明确五件事：解决什么问题、谁使用、输入输出是什么、本期不做什么、怎样算完成。明确指令本身可作为确认来源，不强制追加一轮“请确认”。AI补充本闭环需要的业务对象/规则依据、现成能力检查、最小实现方案、数据权限、失败处理与验证方法；存在业务歧义才询问，普通技术选择自行完成。

门禁只要求 startup_scope_confirmed 的真实确认记录与简表；严格档再要求 risk_review_confirmed。不要求为技术选型、文档数量或每项工程工作分别向用户索要确认。适用的AI证据/降级、语义治理、前端与平台契约仍须在触及该能力前设计，可以先在简表中记录或引用；不必为了开始首个闭环把整个项目全部专项文档标成已确认。

首次闭环验收后继续以 Iteration 扩展，不把 Startup 当作所有后续工作的捷径。范围或验收发生变化必须追溯新授权；无法安全界定闭环则先分析，不大规模编码。

### 日常迭代

本轮变更.json 由AI维护，字段为 change_id、request_ref、baseline_path、baseline_version、scope、impact_reason、impacted_gates、high_risk、business_change、confirmation_ref、validation_plan。保存上一轮记录到已有变更记录后再更新，历史测试和失败样本不得覆盖。基线路径须为 docs 内已确认的唯一源；版本和请求来源必须真实。

impacted_gates 是根据上下文、调用关系和数据流得出的设计门禁数组，不靠关键词自动分类。只列本轮需要新建或更新的需求、业务、架构、数据、复用、验收、回归、测试、AI、语义或交互契约。纯文案或既有样式内调整可以为空，但必须写影响依据与实际验证计划；不得借空数组跳过共享机制变化。

business_change=true 时引用本次真实业务确认；false 时复用原业务授权和当前请求，不新增用户确认。记录索引状态可以为“已记录”，由AI完成，不表示业务批准。高风险变更必须有严格档风险评审；严格项目中已证明隔离且低风险的局部改动只检查本轮影响，不重复整个项目风险评审。

每轮先复用当前有效基线，再更新变化处。测试和文档只覆盖受影响范围，已经冻结的验收要求仍有效；不要求每次跑全部测试，也不能删除、弱化既有测试。影响范围无法确定时扩大调查和回归。

## 能力适用性与上下文范围

PROJECT.yaml 的 applicability 是已确定能力边界的持续来源；不在每轮重新判断全部模块。Startup 确定首期能力，Release/兼容完整评审核对当前整体状态；Iteration 只验证 affected_modules 与 impacted_gates 涉及的能力及其必要依赖。新增、移除或改变能力时更新相关状态、设计、版本和用户授权依据；未知仍为待确认，不能为绕过门禁写不适用。

本轮变更.json 可增加 affected_modules 数组（frontend/backend/ai/semantic_extraction/rag/agent/intelligent_audit/deployment），表示本轮触及的能力，包括启停边界。旧记录缺失此字段按空数组兼容，但须从 impacted_gates 推导依赖；AI 必须如实登记实际影响，不把空数组当作跳过验证的办法。启用/移除 AI、语义或前端契约需列对应设计门禁；RAG/Agent 变化需列 AI 边界门禁。业务或权限变化仍按真实授权处理。

读取从当前请求、清单及相关索引条目出发，沿事实来源和影响链追溯，不整阶段加载。普通搜索和规则解析排除 docs/.staging；只有母版回归、历史对比或用户明确要求才读取其历史内容，且不得作为当前规则来源。

ui.profile 仅前端适用时启用：general-ui 使用通用界面基线；enterprise-web 另执行企业 Web 工作台细则。旧项目缺少此字段时只使用通用基线并提示登记，不推断企业 profile，不降低已冻结 UI 验收要求。frontend-design 是可选外部能力，缺失时按项目基线继续。

## 选择与升级

|档位|适用条件|文档深度|验证要求|
|-|-|-|-|
|轻量|范围明确、低风险、可逆的一次性工具或隔离原型；不涉及下述高风险触发项|通用内容集中在轻量项目执行简表，专项按适用性保留|真实输入到输出的最小闭环、关键异常、受影响边界；记录环境和限制|
|标准|正式业务应用、客户交付、持续维护或既有系统扩展，且没有高风险触发项|按阶段维护已适用文档，只更新受影响内容|主流程、异常、权限、接口和旧功能回归；按实际影响增加性能与兼容测试|
|严格|涉及高风险业务决策、敏感数据处理、权限/安全边界改动、生产数据迁移、不可逆批量副作用，或多租户隔离|标准档加风险评审、独立复核及回滚/补偿验证证据|受影响完整链路和跨模块回归，在目标或等效环境验证；记录差异，现场未验证不得称现场通过|

初始化默认“待确认”，不能根据项目名或关键词自动分类。AI 结合上下文判断并记录选择依据；信息不足先评估，不得默认为低风险。生产故障按严格档处理本次变更。配置平台至少标准档；高风险原型仍需严格控制，可以缩小验证范围但不能降档绕过控制。

PROJECT.yaml 的 execution.profile 使用“轻量/标准/严格”，execution.high_risk 使用“是/否”，rationale 记录依据。档位与证据纳入用户对本期范围的合并确认，无须单独重复提问。新风险出现立即扩大本次控制与验证范围；下调已确认档位或缩减已承诺验收必须记录原因并获得用户确认。

## 所有档位的底线

- 目标、输入输出、业务规则、权限、验收和授权明确，未知保留未知。
- 关键能力先检查现成方案；轻量可以简短记录候选和排除依据，不引入依赖时说明理由。新增依赖的来源、版本、许可证与安全检查不能省略。
- 适用的 AI、语义抽取、平台版本隔离和前端可读性要求不因轻量而失效。
- 不删除目录、不批量删除、不修改冻结样本来通过测试、不自行发布。
- 原型必须记录目的、假设、时间盒和不能证明的事项；产品开发和发布另过门禁。

## 合并维护

轻量档通用的目标、需求、业务、复用、架构、数据、测试与阶段记录可维护在 docs/00-项目治理/轻量项目执行简表.md。独立文档在索引中标记“合并维护”，用途栏登记简表路径及对应章节；原文件保留，不制造第二份持续维护内容。已存在实质内容或多个版本时先比较唯一源，不能自动覆盖迁移。

合并维护不等于“不适用”，不得将适用要求标成不适用。标准和严格档在实际复杂度需要时逐步展开分文档维护，启动期可以合并。已存在的AI能力边界、语义抽取、前端交互等专项继续维护原唯一源；首次开发尚未展开时可在简表记录必要设计及规范引用，不重复建档，不省略专项约束。母版保留完整运维模板；普通 Startup/Iteration 不因文件存在而自动加载或确认。Release 或本轮实际涉及部署运行时启用相关门禁；所有档位发布均保留部署与回滚方案、监控与运行手册、发布检查表；不需要服务部署时在文档中明确本地运行、恢复和交付方式。

## 确认与自主执行

用户决定业务范围、规则、数据权限、验收变化、费用及外部副作用授权。AI 在已确认边界内自主完成可逆的实现选择、布局微调、定位、测试与受影响文档同步，说明判断依据即可，不逐项等待确认。已存在的明确授权引用原记录，不能要求用户重复授权。

将相互关联的业务问题一次集中提出，只暂停依赖缺失答案的工作；可并行推进不依赖答案的检查。不以沉默、超时或 AI 自己填写的状态作为用户确认。无需新决策时复用原确认来源。

## 缺陷与验证裁剪

缺陷处理等级、六问、矩阵和关闭项以 docs/00-项目治理/系统性问题解决方法论.md 为唯一源。简单局部缺陷采用定位、修复、最小充分验证；一般功能缺陷记录原因、影响、修复及相关回归；系统性或高风险缺陷执行完整方法论。安全、跨模块、数据一致性、共享状态和生产故障不得降低为局部问题。

所有关闭项必须有明确结论；适用项提供必要证据，不适用项记录有依据的 N/A，不为不适用项制造证据。简单/一般问题可以在一条执行记录中合并说明未触及的矩阵与关闭项及理由；适用但未运行的项保留“未验证”。不削减冻结测试，结论限于声明的问题、版本和环境。

## 门禁证据登记

门禁证据.json 使用 schema_version=1，records 为数组。每条记录包含 gate、status（已确认）、confirmed_by、confirmed_at、confirmation_ref、evidence_path。gate 对应 PROJECT.yaml 的 governance 字段，不能重复；evidence_path 是项目内 docs 下的非空、已索引唯一源文件，不得指向 .staging 或路径越界。confirmation_ref 写真实用户消息/批准记录或有权限的评审记录定位；禁止伪造。多门禁可引用同一次综合确认，但要能核对各项范围。

完整设计评审 Development 与发布 Release：所有通用确认项与适用专项项，以及 execution_profile_confirmed。Startup/Iteration 使用前述独立入口，不要求本句的所有项目确认。严格档额外 risk_review_confirmed。发布门禁：再加 release_authorized；严格档还需 independent_review_confirmed、rollback_validated。独立复核人不能由实现者冒充；无独立复核条件时保留待确认，不降低档位放行。无数据迁移的严格项目仍需验证制品回退或停用恢复。

脚本仅检查登记结构、路径存在性、状态与档位组合，不判断业务正确性、确认人的权限或批准真实性，也不执行测试。脚本通过后仍须核对原始确认、测试记录和运行证据。草稿、待确认和空白文档不能作为通过状态。
