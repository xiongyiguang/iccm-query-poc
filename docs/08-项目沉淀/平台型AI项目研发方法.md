# 可配置平台项目研发参考（可选专项）

本文件只在项目确实属于可配置产品或平台时参考，不属于所有项目的通用核心门禁。内容来自固定业务 AI 应用与可配置产品研发实践的去业务化复盘，不包含客户数据、具体规则或产品承诺；其中材料、事实、规则、报告仅是一个专项示例，其他业务应替换为自己的对象和运行链路。

## 1. 先判断是不是平台

固定业务应用解决“这类业务如何正确办理”；可配置平台解决“用户如何定义一类业务，并让运行时按冻结版本正确执行”。只要用户能配置材料、事实、规则、流程或报告，项目就不只是多几张管理页面，而是同时存在配置层、版本层和运行层。

|固定业务应用|可配置平台|
|-|-|
|业务对象和规则边界相对固定|对象、事实、规则和报告由配置产生|
|一套完整业务场景可覆盖主要边界|至少两个异构场景才能初步证明通用|
|重点是业务正确性和交付闭环|还要验证元模型、版本快照和运行时解释器|
|改动主要影响既定链路|配置组合、生命周期和迁移产生组合风险|

## 2. 已验证的反模式

1. **先铺配置页面，再补运行时。** 页面看起来完整，但还不能创建真实实例、处理输入、修正、重算和生成结果。
2. **只设计一个演示场景。** 容易把第一个业务的字段和规则悄悄写进“通用”代码。
3. **把阶段完成说成产品完成。** 配置工作台完成、接口返回成功或本机演示成功都不是完整业务验收。
4. **发现解析问题就修改测试材料。** 这会让缺陷消失在样本中，而不会提升真实环境的兼容能力。
5. **按字段或文件逐个打补丁。** 金额千分位、跨行表格、空白日期、签章、扫描件等问题不能靠无限穷举；应提升结构解析、数据类型归一化和模型契约。
6. **每个页面各做一套交互。** 抽屉宽度、拖拽手柄、按钮样式、表单对齐、反馈位置和宽度记忆不一致，会持续产生低级返工。
7. **只测新板块。** 共享任务列表、权限、文件服务、模型服务或公共组件的变化可能破坏既有业务。
8. **不记录服务器基线。** 代码、镜像、升级包和已安装版本混为一谈，后续无法判断应做增量还是整包升级。

## 3. 推荐研发顺序

1. **分类与范围**：确认固定应用、可配置平台、既有平台扩展或原型；明确不允许破坏的旧能力。
2. **场景先行**：在编码前设计验收场景和固定样本。平台至少两个异构场景，每个都含正常、缺失、冲突、替换/删除和失败重试。
3. **契约先行**：定义配置草稿、发布版本、任务实例、输入材料、事实、规则结果、人工操作和报告的稳定 ID、状态和版本关系。
4. **UI 基线**：盘点现有组件，统一按钮、表格、表单、抽屉、反馈、空状态、响应式和状态刷新。
5. **第一条纵向闭环**：只做足以让一个场景从配置到报告真实跑通的最小能力，不同时铺满全部配置页。
6. **变化操作闭环**：验证删除、替换、重新分类、人工修正、启停规则、发布新版本后的失效、重算和历史隔离。
7. **第二场景泛化**：不修改核心模型的前提下配置并运行第二场景；若必须改代码，先判断是通用能力缺口还是业务特例。
8. **旧业务回归**：对共用页面、接口、状态机、存储、文件与模型服务执行回归。
9. **发布门禁**：核对已安装基线、候选制品、目标版本、迁移、备份、回滚和现场验证，不把本机结果当客户环境结果。

## 4. 通用事实抽取的正确分层

事实抽取的难点不应转化为无限业务规则。建议分层：

1. **材料准入与类型识别**：格式、大小、加密/损坏检查，自动分类只给建议，用户替换和明确归类具有更高优先级。
2. **结构解析**：优先读取 Office/PDF 原生段落、表格、单元格、坐标和视觉顺序；扫描件再使用 OCR。
3. **候选事实生成**：由结构定位、标题/标签线索和模型共同生成候选值及证据位置。
4. **按数据类型归一化**：金额、日期、百分比、编号、枚举、布尔、列表分别处理，保留原值和标准值。
5. **确定性校验与冲突**：格式、范围、跨材料一致性、必填和计算使用规则；主观判断才交给模型。
6. **人工确认与学习边界**：人工修改留下前后值、证据和原因；未经治理不能自动变成新规则。

当出现新格式时，修复优先级应为：通用解析/数据类型能力 → 可配置提取策略 → 有明确适用范围的业务规则 → 单一客户特例。任何修复都用原失败样本、结构变体和第二场景验证。
