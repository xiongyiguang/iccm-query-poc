## 本机追加状态与范围契约

合法但缺数据的任务保存pending_business_request草稿及pending_tasks稳定编号；多任务只清除本次实际完成项，未执行或仍失败的分支继续保留。先前成功business_request与当前待补草稿分开；全部待补任务完成才提交整组，明确整组new不继承旧待补任务编号。HTTP、签名续问和前端采用同一状态语义。

PBS根对象范围内的测点是自身及全部后代的实际父链关联集合，走已实现带entity的专用路径；根标识不进入测点自身identity筛选。附加来源/状态/名称筛选独立保留；单个测点属性读取仍是单点定位。页面business_scope来自实际执行依据，删除无条件的“全部测点”标签。

data_insufficient显示“数据不足 · 目标未完成”；未完成草稿保留条件供续问，部分batch不会标记整组目标完成。点选对象时保留未完成任务草稿，不能清掉其他分支。模拟DOM回归覆盖状态应用与筛选范围标签，实际页面缺数据提示、取消条件后Top3及PBS范围772条分别留存；各截图版本与最终结果见公共机制扩展排查V3。前端代码未因模型多轮版本变化重写。

## 0. Profile 与通用 UI 工程

本轮触及界面时读取通用部分。PROJECT.yaml 的 ui.profile=general-ui 适合其他 Web、移动、桌面等界面；enterprise-web 适合企业 Web 工作台，额外启用下文第 1–12 节的场景细则。旧项目未登记 profile 时不推断企业场景，先执行通用基线并依据实际设计登记；原冻结验收继续有效。

通用要求：按实际设备和使用者保障可读性、组件一致性、明确状态、就地成功/失败反馈、错误恢复、键盘/辅助功能或平台等价操作；不得只靠颜色表达状态。优先复用现有组件及平台交互，定义受影响数据状态、刷新和错误处理。界面在实际目标浏览器或原生运行环境验证关键操作、反馈和状态；静态图与编译成功不能代替真实交互。

general-ui 的字号、触控目标、视口/设备、布局、表格密度和主操作数量根据产品及目标平台确定，记录依据和真实验证；不强制 24px 间距、固定桌面视口、工作台分栏或每页唯一主操作。第 13–16 节用作项目登记和验证记录，矩阵只启用本轮及当前 profile 实际存在的控件/状态。

frontend-design 是可选外部 Skill：可用且适合当前任务时可调用；不可用则按本项目基线继续，不阻塞普通研发，不复制用户级技能，不绑定本机路径或要求安装。已有设计稿直接按参考实现。

## 企业 Web 工作台细则（仅 enterprise-web）

下列第 1–12 节面向后台管理、业务工作台、表单与配置平台。品牌规范可替换默认令牌；通用可读性、状态语义和已冻结验收不降低。

## 1. 先确定设计任务，不从组件拼装开始

编码前先写清四件事：

1. 具体产品主题是什么；
2. 谁是主要用户，谁是次要用户；
3. 当前页面唯一要帮助用户完成的工作是什么；
4. 用户完成工作必须看到的状态、证据、操作和反馈是什么。

常规后台、表单和工具类 UI 优先清晰、效率和稳定；可选外部 Skill 按第 0 节处理。只有高端品牌展示、视觉方向未定或需要明显创意探索时，才先生成多个视觉方向；已有截图、Figma 或明确设计稿时直接按参考实现，不重复探索。

每套界面可以有一个有依据的识别点，例如证据联动、阶段轨道或独特的数据组织方式；其余部分保持安静。不要用渐变、发光、悬浮卡片、英文眉题和无业务含义的编号制造“设计感”。

## 2. 空间效率总原则

紧凑不等于缩小。节省空间的优先顺序固定为：

1. 删除重复标题、重复编号、重复状态和装饰性说明；
2. 按当前任务只展示必要信息，异常和待办优先，通过项汇总折叠；
3. 把技术编号、版本、耗时和日志放入就近的可展开详情；
4. 合并同类工具条、筛选项和操作；
5. 使用合理的分栏、稳定网格和内部滚动；
6. 最后才微调间距，禁止通过小于可读下限的字号换取首屏行数。

首屏应看到页面身份、关键状态、唯一主操作和第一组可处理内容。页面只保留一个主滚动条；表格、材料预览或代码详情可在边界明确时内部滚动，但不得形成三重滚动。

## 4. 字体、字号与控件尺寸

### 4.1 默认字体

```css
font-family: "Microsoft YaHei UI", "Microsoft YaHei", "PingFang SC", sans-serif;
```

技术编号、版本和短代码可使用：

```css
font-family: "SFMono-Regular", Consolas, "Liberation Mono", monospace;
```

等宽字体只用于真正的技术信息，不用于中文业务标题和大段正文。

### 4.2 推荐尺寸

|角色|字号/行高|说明|
|-|-|-|
|页面标题|28px / 1.3|一页一次，不重复标题|
|区块标题|18px / 1.4|稳定表达信息层级|
|卡片标题|15–16px / 1.45|避免每张卡都做成大标题|
|正文、表格主内容|14px / 1.55–1.65|企业操作界面的默认阅读尺寸|
|表单控件、按钮|14px；高度 40px|次级行内操作最低 36px|
|次要说明、状态辅助|12–13px / 1.5|不得承载唯一关键结论|
|技术编号、版本|12px / 1.45|等宽字体，可折叠|

操作界面禁止使用小于 12px 的可见文字。桌面点击目标最低 36px，主要按钮和输入控件最低 40px；移动或触控场景宜提高到 44px。不要先写大量 8–11px 样式，再用全局 `!important` 覆盖修正。

## 5. 间距、宽度和密度令牌

- 使用 4px 基础节奏：`4 / 8 / 12 / 16 / 20 / 24 / 32 / 40`。
- 页面最大内容宽度默认 `1520px`；桌面左右内边距约 40px，1280px 以下约 28px，760px 以下约 16px。
- 区块间距默认 20px；卡片内边距 16–24px；工具条 12–18px。
- 主要内容与浏览器边界之间必须留白；表格首列左侧和末列右侧默认 24px。
- 圆角以 4–6px 为主；阴影只用于浮层或明确抬升关系，不让所有卡片漂浮。
- 使用 `box-sizing: border-box` 和 `scrollbar-gutter: stable`，避免滚动条出现时页面左右跳动。

大面积空白里放一个很小的卡片不是“简洁”；应让主要业务容器合理占用可用宽度。相反，不能为填满空间而平铺技术日志和历史版本。

## 6. 页面与导航结构

- 每页一个主要任务、一个明显主操作；查询、取消、编辑等为次操作，表格低频操作使用文字按钮。
- 顶部导航表达系统级工作区；页签表达当前对象内部组成。不要让局部页签偷偷切换到另一个顶层工作区。
- 多阶段任务共用稳定的任务身份区和阶段导航；切换阶段只替换下方工作区，避免页头高度、任务名称和横向位置跳动。
- 面包屑表达位置，阶段条表达进度，不在页头重复任务号、页面名和阶段名。
- 技术详情保留但降级显示，不能为了“干净”删除审计、版本或证据能力。

## 7. 表格与列表

表格先定义“每列的业务职责”，再定宽度。不同语义的表格必须使用各自的列宽契约，禁止共享脆弱的全局 `nth-child()` 宽度规则。

- 表头建议高度 48px，正文单元格上下内边距约 12–13px。
- 规则名、说明、业务结论和方案名允许自然换行，不用省略号隐藏主要业务信息。
- 技术 ID、哈希和长文件名可以省略，但必须能通过详情、复制或悬停查看完整值。
- 状态标签保持内容宽度；操作列可以换行排列，按钮文字自身不拆行。
- 1366px 及以上不允许页面级横向滚动；更窄时只允许表格容器内部滚动。
- 首列、末列及分组行左右各保留 24px，避免内容贴边。
- 分组标题用一条轻量行即可，不为每组增加大面积卡片头。

## 8. 工作台分栏、抽屉与分隔条

材料/证据与审核结果等需要并行核对的内容，可使用可调分栏：

- 桌面默认约 50/50，建议限制在 32%–68%，确保两侧始终可操作；
- 垂直分隔条可用约 12px 命中宽度，视觉线可以更细；
- 分隔条必须使用真实独立控件和 `role="separator"`，支持鼠标/触控、方向键、Home/End、双击复位；
- 比例可以本地保存，但用户必须能够恢复默认值；
- 约 1040px 以下改为上下排列，隐藏拖动条；
- 抽屉内上下区域需要调节高度时，同样使用独立横向 splitter，禁止拿表单边框伪装拖拽区。

抽屉和弹窗要限制最大高度并明确内部滚动区域。关闭、取消、保存和失败反馈的位置必须稳定，不能因内容高度变化而离开视口。

## 9. 状态、反馈和界面文案

- 主界面显示用户能理解的业务状态；内部枚举、布尔值、模型字段名只放技术详情。
- 同一个动作在按钮、进行中状态和完成提示中使用同一个动词，例如“发布 → 正在发布 → 已发布”。
- 错误出现在触发操作附近，说明发生了什么、哪些内容未改变、用户下一步做什么；不能只在另一个页面写日志。
- 空状态要给出下一步入口，不写只有情绪没有行动的空话。
- 禁用操作要让用户知道原因和解除条件。
- 默认优先显示异常、待确认和待处理项；正常项可汇总折叠，但必须可展开追溯。
- 展示层必须理解真实数据语义。比较另一个字段时，应显示比较对象和当前值，不能误读未使用的固定 `null` 并翻译成“空值”。

## 10. 响应式与无障碍

至少设计并验证以下视口：`1366×768`、`1440×900`、`1920×1080`，以及项目需要的窄屏。推荐以约 1280、1040、760px 为主要布局变化点，并集中维护，避免同一断点散落多份冲突规则。

- 所有交互元素有清晰的 `:focus-visible`；
- 拖拽必须有键盘等价操作；
- 状态不能只靠颜色；
- 动画遵守 `prefers-reduced-motion`；
- 文字放大、长中文、英文代码、空值和极长文件名不得破坏布局；
- 窄屏优先改为单列或内部滚动，不通过整体缩放页面解决。

## 11. CSS 与组件工程规则

- 颜色、字体、间距、高度、圆角、阴影和断点先形成令牌，再实现页面。
- 公共组件承担按钮、表单、状态、空态、反馈、表格、弹窗、抽屉和分隔条的一致性；业务页面只组合，不重复造轮子。
- 避免用一个持续增长的全局 `styles.css` 承载全部页面。按令牌、基础、布局、公共组件和业务模块拆分，并明确加载顺序。
- 不把“在文件末尾再覆盖一层”当作常规修复；新增 `!important` 必须说明原因并有移除计划。
- 不使用作用域过大的元素选择器或 `nth-child()` 影响无关页面；优先使用组件类和语义类。
- 任何视觉修复都检查同类页面和不同数据长度，不能只针对截图中的一行、一列或一个分辨率。

## 12. 已验证的常见失败模式

|失败模式|表面现象|根因|以后怎么做|
|-|-|-|-|
|把紧凑理解为缩小字号|首屏行数增加，但中文、状态和证据难读|没有先删重复信息和调整层级|正文/表格保持 14px，辅助信息不低于 12px；先折叠技术信息|
|后置覆盖层越来越大|同一属性多次定义，靠 `!important` 才生效|样式未模块化，选择器职责混乱|建立令牌和组件样式；修复归位到最低公共层并删除过期规则|
|不同表格共用列序号宽度|换一个页面就错列、挤压或截断|按 DOM 序号而非业务列定义|每张表单独建立列职责与宽度契约|
|表格内容贴左右边界|视觉拥挤，即使列宽足够仍难读|忽略表格容器边界留白|首末列和分组行左右保留 24px，先局部修复再考虑改列宽|
